**ICache / DCache 分阶段实施方案：先实现 Cache，后接入 MMU**

最新执行计划见 [基于当前 AXI4-Lite SoC 的 Cache 接入计划](cache_integration_plan.md)。下文保留原始规划；其中 P1 握手、LSU、AXI 后备和取指吞吐优化已完成，不再作为待开发前置任务。

编写日期：2026-10-19。本文保留原始实施计划。进度更新（2026-10-21）：P1 握手基础已实现；按用户选择，后备路径先接入共享 AXI4-Lite，已实现 LSU、逐字仲裁和 RAM/UART 两从设备连接，详见 [AXI RAM 实现与验证](axi_lite_ram.md)。后续已优化取指及主桥交接，CoreMark CPI 从 8.3503 降到 2.0672，见 [优化记录](axi_lite_optimization.md)。ICache、DCache 和 MMU 仍待实现。

当前里程碑是在现有 RV32 单发射 CPU 上完成可验证的 I/D Cache。后续接入 MMU，并保留多发射、乱序执行的扩展路径。当前阶段先使用地址直通模块，无需先实现 MMU，也不在 Cache 阶段同时改造发射宽度。

**1. 当前代码与需要优先处理的依赖**

| 当前实现 | 对 Cache 接入的影响 | 计划处理 |
|---|---|---|
| vsrc/mem/dataram_banked.v 将指令、数据放在同一份双 bank RAM 中，每 bank 32 KiB | 指令与数据必须保留共同的后备存储；文件头部分容量注释与参数不一致 | 以 BANK_ADDR_WIDTH=13 为准，保留现有镜像格式与 64 KiB 容量 |

| top.v 的 top_core_mem_stall 当前来自 UART 桥 | 缺少独立的指令等待、数据等待控制 | 分开管理前端停止供指、MEM 等待和后备存储运行 |
| WB 和 MEM->EX 旁路直接使用 dataram_core_rdata | 可变延迟返回可能与 rd、PC 或下一条指令错位 | load 返回数据随指令进入 MEM/WB；旁路增加结果有效条件 |
| 多个流水寄存器暂停时保持写使能与操作码 | 等待期间可能重复触发写回、CSR 或控制事件 | 建立有效位、接受事件和已发送状态，逐项核查一次性副作用 |
| ex.v 已有乘除法结果保存与接受控制 | 新访存等待不能破坏既有握手 | 复用已有结果保持机制，扩展与访存等待重叠的验证 |
| mem_to_axi_lite_bridge.v 通过 wait_req_release 等待请求电平释放 | 不能把连续的 ready/valid 事务直接映射成一直为高的旧请求 | 增加适配器，完成请求释放；覆盖连续 UART 访问 |
| tohost 由后备 RAM 中固定地址写入触发 | 后续写回 Cache 会延后测试结束信号 | 单独定义整行不可缓存的测试出口属性 |
| 当前 fence.i 包含重定向与预测器失效 | Cache 接入后还需协调在途取指、失效与写可见性 | 增加独立维护请求和完成应答 |

上述内容是接口改造的检查点；需要通过定向验证判断旧控制在新增等待下的实际行为。

**2. 第一版应完成的配置**

| 参数或行为 | 第一版决定 | 后续扩展 |
|---|---|---|
| 地址组织 | 物理索引、物理标记，PIPT | MMU 翻译后继续使用同一物理 Cache 接口 |
| 虚拟/有效地址宽度 | VADDR_WIDTH=32 | 独立于物理地址宽度 |
| 物理地址宽度 | PADDR_WIDTH=34；当前地址零扩展，合法区域仍为现有 RAM/UART | 给 Sv32 预留；地址译码检查全部高位 |
| ICache / DCache 数据容量 | 各 4 KiB | 容量参数化，后续用数据决定扩容 |
| 相联度 | 两路，每组一位 LRU | 暂时只承诺支持两路，避免无验证的任意路数参数 |
| 行大小 | 32 B，8 个 32 bit 字 | 行大小参数化并约束为 2 的幂 |
| 组数 | 4096 / (2 × 32) = 64 | 编译时检查参数是否合法 |
| ICache 输出 | 每次一个 32 bit 指令 | 可扩展为 64 bit 对齐块与两位有效掩码 |
| DCache 端口 | 一个 32 bit 对齐字接口，带 4 bit 字节写使能 | 多发射初期仍可保留一个 LSU |
| 缺失并发 | 每个 Cache 一个 miss；功能版限制请求并发 | 后续增加查询流水和多个 MSHR |
| DCache 写策略 | 写直达、不写分配；写完成才应答 | 按带宽瓶颈决定是否升级写回、写分配 |
| 后备接口 | 32 bit 对齐字请求/响应，初版只允许一个全局在途字事务 | 可扩展 AXI4；外设沿用 AXI-Lite |
| 旁路配置 | I/D Cache 分别可关闭；模式切换在复位时固定 | 运行中切换需维护协议，另行实现 |

地址划分以物理地址宽度为准：行偏移 5 bit，组索引 6 bit，Tag 宽度为 PADDR_WIDTH-11。默认 34 bit 地址时为 tag[33:11]、index[10:5]、offset[4:0]，Tag 共 23 bit。若改成 32 bit 物理地址，Tag 才是 21 bit。

第一版允许查询与响应占用多个周期，不将“同步 RAM 一周期读出”等同于“整个 Cache 每周期接受一个请求”。后者在功能正确后单独优化和验证。

Cache 数据 RAM 使用同步读、字节写使能；复位主要清除 Valid、控制状态和队列，不复位整个数据阵列，以便保留 BRAM 推断。Tag/Valid 可先使用小型寄存器阵列，后续按综合结果调整。

**3. 模块关系与职责**

当前阶段的取指路径：

    取指前端 -> 地址直通 -> 物理属性译码 -> ICache/取指旁路
              -> 后备存储仲裁 -> 后备 RAM

当前阶段的数据路径：

    MEM -> LSU -> 地址直通 -> 物理属性译码 -> DCache 或不可缓存访问
             -> 后备 RAM / 现有 UART 桥

未来启用 MMU 时，地址直通的位置改为 TLB、页表遍历和权限检查，后面的物理 Cache 接口保留。VA 对应的指令 PC、访存故障地址由前端/LSU 保存，不能被返回的 PA 替代。

地址翻译边界保留有效地址、访问种类（取指/读/写）和请求 ID，返回 PA、同一 ID 及翻译故障状态。当前直通实现只做零扩展并传递背压，可以用组合逻辑完成，不要求新增翻译延迟或模拟一个尚未实现的 TLB。未来特权上下文由 MMU 接收，不放入 Cache 的替换状态。

**4. 请求、响应与作废规则**

Cache 前端物理字接口建议包含：

| 信号 | 方向 | 语义 |
|---|---|---|
| req_valid / req_ready | 请求握手 | 上升沿两者同时为 1 接受一次请求 |
| req_id[REQ_ID_WIDTH-1:0] | 请求 | 由前端或 LSU 分配，响应原样返回 |
| req_addr[PADDR_WIDTH-1:0] | 请求 | 对齐的物理字地址 |
| req_write | 请求 | 0=读，1=写；ICache 固定为 0 |
| req_wdata[31:0] | 请求 | 已按字节位置摆放的写数据 |
| req_wstrb[3:0] | 请求 | 有效写字节；读请求按接口约定置零 |
| rsp_valid / rsp_ready | 响应握手 | 完成信息被消费一次 |
| rsp_id | 响应 | 对应被接受请求的 ID |
| rsp_rdata[31:0] | 响应 | 原始对齐字，扩展/拼接在 LSU |
| rsp_err | 响应 | 当前请求失败，错误数据不可当作有效 load |

建议 REQ_ID_WIDTH 初始为小型可配置值，例如 4；它不表示首版同时支持 16 个请求。首版仅分配允许的一个请求，后续由队列管理更多 ID。

协议规则：

1. req_valid=1 且 req_ready=0 时，请求字段保持稳定；重定向后的旧取指可以先完成握手再丢弃，也可以用独立的取消握手撤销，初版选前者，避免破坏协议。
2. 请求被接受后，CPU 可以撤销 req_valid；Cache 保存必要字段。Cache 接受一次后只产生一次响应，读和写都需要完成响应。
3. rsp_valid=1 且 rsp_ready=0 时，响应字段保持稳定。Cache 不能依赖流水线恢复运行才能推进补行或总线应答。
4. 每个被接受的 Cache 请求最终都要完成响应；指令被分支作废时，消费者仍吸收对应响应，只是不更新有效流水状态。
5. 请求 ID 在原响应被吸收前不能复用。未来允许更早复用时，必须增加代际信息；仅靠一个会反复翻转的位不能保证无限次重定向下无混淆。
6. 前端维护 valid/killed 标记。普通分支仅作废指令归属，不要求取消已经开始的外部读，也不要求清空 ICache。
7. LSU 保存有效地址、PC、大小和符号属性；Cache 只需识别访问缓存行和请求 ID。未来 ID 到 ROB/Load Queue 的映射放在 LSU。

维护接口单独定义，例如 maint_valid/maint_ready、maint_op、maint_done。接受维护与维护完成是两个不同事件。整缓存失效只在所有目标 Valid 已清除、相关旧补行已被处理后报告完成。

后备物理字接口同样采用握手，增加 source/owner 记录；Cache 内部通过 beat_index=0..7 发出一条行的 8 个字。初版按单字事务轮询仲裁，锁定归属直到该字响应被缓存/消费者接受，再切换请求源。每个 Cache 自己记录补行进度，允许 I/D 的不同字事务交错；初版不需要突发总线。

读返回可以交错属于不同 Cache，但单个 Cache 内只存在一条在途补行。以后替换成 AXI4 burst 时，适配层再负责长度、last 和响应路由，不能把 AXI-Lite 当成原生多拍突发接口。

**5. 流水线推进与精确状态更新**

取指停顿与数据停顿分开处理：

- ICache 缺失或前端队列空：停止新指令进入 ID，已有后端指令继续完成；不能把这一条件直接并入现有全局 stall 冻结全部流水线。
- DCache/不可缓存访问未完成：MEM 保存当前指令、请求状态和结果，上游按背压等待；WB 中较老的有效项可以完成并清除 valid。
- 后备存储、补行和响应缓冲独立运行，不使用 core_stall 作为时钟使能。

建议统一推进事件：stage_fire=stage_valid && stage_ready。实际实现可保留现有 stall/flush 端口，但必须明确它们与 fire、有效位及消费之间的关系。

需要逐项完成的控制改造：

1. 一条访存指令至少记录 not_sent、waiting、completed 三种事务状态；req_valid 只在未发送时有效。不能根据仍保持为高的 load/store 操作码反复发请求。
2. load 的返回数据、目标寄存器、PC、异常状态和 valid 一起进入 MEM/WB。WB 不再直接使用随外部响应变化的实时 dataram_core_rdata。
3. MEM->EX 旁路只在来源有效、需要写 rd、且结果就绪时生效。load 等待时既不能旁路旧数据，也不能让消费者越过等待。
4. 寄存器写使能由有效提交事件限定；WB 项完成后清除 valid，避免停止期间重复更新架构状态。
5. 分支训练、CSR 写、trap/mret 控制、fence.i 维护启动以及乘除法事务接受都使用明确的一次性事件。CSR 若在 EX 更新，应保证较老访存已完成且没有异常；后续改成提交更新时再集中迁移。
6. 将 minstret 的计数点统一到被确认无异常的架构提交事件；不再只以 MEM->WB 有效项前进等同于所有情况均已退休。mcycle 在等待期间继续计数。
7. 已被接受的重定向需要在取指背压下保存目标，直到新 PC 请求可发出。较老 MEM 等待时尚未被接受的较年轻 EX 控制事件不反复触发。
8. 较老访存异常优先于较年轻分支/CSR 更新；清除较年轻指令。对外已提交的 store 不因较年轻分支而取消。

推测取指错误先作为带 PC 的故障项进入前端/流水线；到达安全的异常处理位置时才触发 trap。如果故障项随后被较老分支作废，就丢弃该错误，不能因错误路径的预取立即打断正确程序。

改造先以可变延迟直接 RAM 验证。此时尚无 Cache miss，能够把流水线握手问题与替换/补行问题分开定位。

**6. ICache 的具体实现顺序**

1. 定义每路 64 项 Tag/Valid，以及每路 512 个 32 bit 字的数据 RAM。数据地址为组索引与行内字索引的组合。
2. 功能版先实现单请求控制：接收 -> 同步读/查询 -> 命中响应，或选择 victim -> 补行 -> 响应。
3. 两路先选无效路，均有效时按每组 LRU 选 victim；命中和成功安装后更新 LRU。首版只在全部 8 个字成功返回后安装 Valid。
4. 补行地址始终由保存的 line_base 和 beat_index 计算，不使用当前可能已经变化的 CPU PC。
5. 任一拍错误时，不安装部分行；吸收当前已发出的响应，向对应请求返回错误。首版不使用 critical-word-first 或 early restart。
6. 普通分支发生后，将前端旧请求记为 killed；已开始补行可以完成并安装，旧指令响应不进入有效队列。
7. fence.i 使用与普通分支不同的维护流程：停止新取指，等待/排空旧补行与响应，清除全部 Valid，清空队列，再从下一 PC 取指。初版通过串行等待避免失效完成后旧补行重新安装。
8. 复位先清 Valid；若 Valid 改成同步 RAM，使用初始化遍历并在完成前阻止正常查询。无需清零数据 RAM。

第一版不要求请求/响应重叠。性能阶段将查询和返回分级，并为输出准备缓冲，在响应背压时停止继续读出无法保存的结果。

**7. DCache 与 LSU 的具体实现顺序**

LSU 将普通 RAM 的访问转换成一个或两个对齐字操作：

- LB/LBU：选取字节后做符号/零扩展。
- LH/LHU/LW：根据有效地址低位选择与合并，跨字时先低地址、再高地址。
- SB/SH/SW：生成每个字的摆放后 wdata 和 wstrb，跨字时拆成两次字请求。
- 原始指令在全部必要子请求完成后只应答一次；第二个请求失败时保留原始指令 PC 与对应故障信息。
- RAM 末尾越界、RAM 到 MMIO 的跨区域访问，在发送第一笔写之前检查整个范围；禁止通过截断 bank 索引绕回低地址。
- MMIO 访问按外设支持的大小和对齐规则处理；禁止自动跨寄存器、跨区域拆分。现有受支持的字节写行为需要回归保留。

第一版 DCache 行为：

| 请求 | 命中 | 缺失 |
|---|---|---|
| load | 返回原始字 | 从 RAM 读完整行，成功后安装并返回 |
| store | 向后备 RAM 写入；成功后按字节更新命中行并完成 | 只写后备 RAM，成功后完成，不分配行 |

先等待写成功再更新命中缓存行，简化错误恢复；写等待期间不接受可能观察到不一致状态的新数据请求。若后备写报错，保守失效相关缓存行，返回错误；不将失败写当成成功完成。

首版补行缓冲可以保存完整 32 B 行，或逐字写入被暂置无效的 victim；两种方案都必须等全行成功后置 Valid。选择以资源与时序报告为依据，接口不受影响。

后续写回版本增加 Dirty 和写回记录。脏 victim 的 Tag、组号、数据在写回成功前必须保留；部分拍失败时不能清 Dirty 或用新行覆盖。写回完成后才进入新行补行。该版本需要单独验证写回错误、整缓存 clean 和 fence.i，不与第一版写直达混在同一个变更中。

**8. 物理地址属性、测试出口与错误**

| 物理范围 | 属性 | 行为 |
|---|---|---|
| 0x8000_0000..0x8000_FFFF | 普通 RAM，测试出口行除外 | I/D 可缓存，来自同一后备 RAM |
| 0x8000_1000..0x8000_101F | 当前 32 B 行配置下的 tohost 行 | 数据访问整行不可缓存；复用 RAM 字接口 |
| 0x1000_0000..0x1000_000F | UART MMIO | 不缓存、不预取，按序访问现有桥 |
| 其他地址或超出实现 PA 范围 | 非法 | 显式报错，不访问截断地址 |

tohost 行边界由 TOHOST_ADDR 和 LINE_BYTES 计算，避免行大小调整后只排除一部分行。同一物理行的访问必须使用一致缓存属性。取指只允许已定义的可执行 RAM 区域，不对 UART 发出推测取指。

tohost 在对应 CPU store 真正成功时产生测试完成事件；来源为明确的数据写事务，不能把任意补行或以后写回的流量误认作新提交。若将来工具链改变 tohost 符号位置，应由测试配置/符号解析提供地址，统一更新监控与属性。

Cache/总线错误分层返回：后备错误 -> Cache/旁路 rsp_err -> 前端/LSU 保存 PC 和故障地址 -> 精确异常。计划补全指令访问错误、load 访问错误、store 访问错误的 cause 与 mtval 保存；错误路径必须纳入首版验收，不能仅依赖测试超时发现问题。

组件调试初期可以将错误直接报告为仿真失败，但完整系统验收前必须接通架构异常，并确认故障指令不退休、较年轻指令无副作用。

**9. FENCE 与 FENCE.I 的维护流程**

写直达功能版不设延迟提交的 store buffer。普通 FENCE 先采用保守的全访存串行化：等待更早数据读写和 MMIO 完成，再允许后续相关访问推进。它与 ICache 失效、未来的 SFENCE.VMA 使用不同控制操作。

写直达版本的 fence.i：

    接受一次 fence.i
      -> 停止发出新取指并标记旧前端项无效
      -> 等待较早数据事务完成
      -> 排空在途旧取指与补行，吸收旧响应
      -> 逐组清除 ICache Valid
      -> 确认维护完成，保留现有预测器失效动作
      -> 从 fence.i 的下一条 PC 重新取指

后续写回版本在 ICache 失效与重新取指之前增加 DCache 全部脏行 clean，并确认后备写完成。初版选择顺序遍历全部组，后续再考虑范围维护或监听。

Cache 维护状态机必须独立于 core 的等待状态运行，否则可能出现“CPU 等维护完成、维护又等 CPU 解冻”的死锁。

RISC-V 对 fence.i 的核心要求是后续取指能看到当前 hart 更早的写入；以上是本项目选择的保守实现。依据：[Zifencei 规范](https://docs.riscv.org/reference/isa/v20260120/unpriv/zifencei.html)。

**10. 实施里程碑与进入下一阶段的条件**

| 阶段 | 主要交付 | 验收条件 |
|---|---|---|
| P0 基线 | 固定配置、当前结果、性能窗口、资源基线 | 原工程回归可复现，失败/排除项有记录 |
| P1 流水线与握手 | 请求/响应、load 结果寄存、一次性副作用、有效提交 | Cache 关闭，固定和随机等待下原测试正确，无重复访存 |
| P2 存储后端与 LSU | 原始字 RAM、仲裁、非对齐拆分、MMIO 适配、地址直通 | 数据边界与 UART 语义正确，I/D 并发无丢响应或饥饿 |
| P3 ICache | 两路查询、补行、替换、前端队列、旧取指作废 | ICache 开/DCache 关，定向与 ISA/BP 回归正确 |
| P4 DCache | 写直达、不写分配、字节更新、跨行访问 | I/D 全开与 D-only 配置均正确；与参考内存一致 |
| P5 维护与异常 | fence/fence.i、tohost、错误异常、完整日志 | 自修改代码、故障、在途维护全部通过；无静默卡死 |
| P6 性能优化 | 命中流水、带宽测量；按证据决定写回版本 | 功能回归保持，通过频率/资源/程序时间比较证明取舍 |
| P7 MMU | Sv32、TLB、页表遍历、权限和页故障 | 关闭 MMU 等价回归，启用后独立验证翻译与异常 |
| P8 多发射/乱序扩展 | 供指宽度、发射与提交；可选队列与非阻塞 Cache | 每项独立里程碑，避免与 MMU/写回同时首轮接入 |

P0..P5 构成当前 Cache 功能版。P6 的流水优化与写回是两个独立任务；是否先写回再接 MMU由测量与项目目标决定。P7、P8 是后续路线，不是开始写 Cache 的前置条件。

P1 可先给现有 dataram_banked 加临时握手适配，保留旧访存操作类型，以验证请求接受与返回数据保存。P2 再将其替换为 LSU 加原始字 RAM。这样不要求在验证第一条握手请求前同时完成全部后端重构。

建议按以下顺序拆分变更：基线记录；访存握手与结果保存；一次性控制与精确错误；后备字 RAM/LSU/MMIO；ICache；DCache；屏障与维护；测试汇总；性能优化。每次保持已有功能回归可运行，必要时通过复位配置切换新路径。

单元级检查既要有参考内存比较，也要有事务记账。参考内存按字节保存，与 Cache 的 Tag/Data 组织独立，避免测试只复述实现。

建议第一批汇编用例使用明确名字：icache_cold_hit.s、icache_conflict.s、icache_redirect_miss.s、dcache_load_store.s、dcache_byte_mask.s、dcache_cross_line.s、cache_fencei_patch.s、cache_minstret_stall.s。低层随机背压和故障注入由 SV testbench 覆盖，不要求每种故障都用汇编模拟。

ISA 成功判据仍为 tohost=1；0 为未完成，其他非零为失败。不通过 --skip-fencei 掩盖 Cache 维护问题；若环境确有排除，摘要必须记录。

**12. 性能指标与比较方法**

保留三个基础对照：原始直接 BRAM；新握手路径但关闭 Cache；新握手路径启用 Cache。这样能区分接口改造开销与缓存本身的影响。

统一架构提交计数和性能窗口后再报告可比的 CPI。若 P1 修正旧退休计数口径，需要同时说明差异，并用同一窗口重新建立对照，避免把计数点变化当作性能提升。

测试实际 BRAM 时序与额外等待模型；同一轮比较必须使用相同后备内存模型、程序、编译选项和性能窗口。模拟慢内存的收益单独报告，不当作当前 FPGA 实测收益。

建议记录：

- mcycle、minstret、CPI；CoreMark 的 CRC 与相同性能窗口。
- I/D 接受的可缓存请求数、命中数、缺失数；MMIO、旁路、补行拍数独立计数。
- ICache 缺数据导致的前端空转周期、DCache 等待周期、仲裁等待与 MMIO 等待周期。
- 后备读字数、写字数、平均补行耗时；后续写回增加脏行写回次数。
- 综合后的 Fmax、LUT/FF、BRAM 用量；程序耗时按周期数与相应时钟频率共同评估。

统计在 req_fire 等明确事件更新一次。缺失请求在状态机等待期间不反复计数；跨字 LSU 请求数与架构 load/store 指令数分开。推测取指可计入访问统计，但需明确分母定义。

对无定时/外设轮询依赖的定向程序，启用 Cache 前后应保持退休指令数与架构结果一致；CoreMark 总指令数可能受 UART/计时循环影响，应以固定计算窗口和 CRC 比较。不同停顿来源可以同时发生，若展示总和，使用互斥优先级桶并另记原始事件，不能直接把重叠计数相加。

性能优化按测量顺序进行：先改善命中查询/响应重叠，再评估供指带宽和后备写流量，最后决定缓存容量、行大小、写回和预取。每项只改变一个主要因素，重复相关正确性验证。

**13. 后续 MMU 如何接入**

PIPT 第一阶段无需改变 Cache 的基本寻址机制。先将地址直通替换为 ITLB/DTLB，未命中时由页表遍历器读取物理页表，得到 PA 和权限检查结果再发出正常缓存访问。

后续 MMU 还需实现 Sv32 的 satp、页表格式、权限与 A/D 策略、S/U 模式相关 CSR/陷阱以及 SFENCE.VMA。它是完整的独立功能阶段，不等于插入一个组合地址转换模块。Sv32 使用 32 bit VA，物理地址可达 34 bit，因此本方案分开参数化 VA/PA。依据：[Supervisor 规范](https://docs.riscv.org/reference/isa/v20260120/priv/supervisor.html)。

页表遍历请求必须走物理访问通路，不能再次送入虚拟地址翻译。若后续 DCache 已采用写回，页表遍历需要读取同一 DCache 的最新内容，或实现等价的可见性机制；只读陈旧后备 RAM 会丢失尚在脏行中的页表更新。初版建议物理 PTW 端口仲裁接入 DCache，并保证当前虚拟请求等待翻译时不会占死其必需的请求资源。

跨页的非对齐访问由 LSU 分别翻译相关页面，不能假设第二个物理页与第一个物理页连续。对拆分 store，建议先完成所有子访问的翻译、权限与范围检查，再发出写入；不承诺跨字普通访存原子性。

SFENCE.VMA 管理地址翻译缓存及在途页表遍历的失效语义；它与 FENCE.I 的取指一致性职责分别实现。物理标记的 Cache 不应仅因切换 satp 就无条件全部清空；是否维护取决于具体操作与物理属性。

未来若追求 TLB 查询与 Cache 阵列并行，再评估 VIPT。当前 4 KiB、两路、32 B 行使用 index[10:5]，落在 4 KiB 页的页内偏移范围，但改为 VIPT 仍需验证物理 Tag、权限时序和同义地址行为，不能只改端口名。

**14. 后续多发射与乱序如何扩展**

供指先扩为每周期一个 64 bit 对齐块，携带两位指令有效掩码和各自 PC；跳转到块上半字对应的 32 bit 指令时只标记该槽有效。配合 4..8 条指令队列，之后再设计每组最早控制流预测和双译码。

多发射不要求同时提供两个 DCache 端口。先采用一个 LSU，同周期最多一条访存；多条访存按发射资源约束分开发出。寄存器端口、同组依赖、旁路和 0/1/2 条提交统计属于核心独立改造。

若选择乱序执行，先建立寄存器重命名、ROB、发射队列与顺序提交，再逐步扩展 LSU：

1. 用 Load/Store Queue 保存请求归属，req_id 映射到队列和 ROB。
2. 普通 load 可在满足依赖检查后推测执行；较老 store 地址未确定时先采用保守等待，后续才加入推测与重放。
3. store 先保存地址和数据，获得提交授权后才对普通缓存数据或外设产生不可撤销的写效果。
4. 分支恢复作废较年轻 load 的指令结果；已开始的缓存补行可完成，但不能更新已被作废的目的寄存器。
5. MMIO 读写因存在副作用，等待安全的提交条件并按序执行。
6. 先让乱序核心在阻塞 DCache 上通过功能，再逐步加入 hit-under-miss、多 MSHR、同一行缺失合并与容量不足的背压/重试。

这些属于后续能力，当前只固定请求 ID、响应归属、LSU 边界与维护协议。Cache 不需要携带完整 ROB 数据结构。可参考：[BOOM LSU](https://docs.boom-core.org/en/latest/sections/load-store-unit.html) 对队列、提交授权和数据转发的职责划分。

**15. 当前阶段完成的定义**

- P0..P5 的实现与证据齐备，单发射 CPU 在可变延迟内存下正确执行。
- I/D Cache 启停四种组合通过适用的 ISA、UART、BP、minstret 回归。
- 自修改代码与 fence.i 正确；在途补行不会在维护后恢复旧内容。
- 普通 RAM 访存语义保留，跨行访问、非法地址与总线错误有明确结果。
- 架构提交、CSR、UART 和 store 等副作用只发生一次，错误或已作废指令不提交。
- 性能报告分开说明接口开销、真实 BRAM 条件与模拟慢内存条件，不预设 Cache 必然提速。
- 后续 MMU 能通过替换地址直通并增加物理页表访问接入；不把它作为当前 Cache 功能版的先决条件。
